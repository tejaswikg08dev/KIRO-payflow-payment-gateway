## How API Key Authentication Works

```
EVERY payment API call from a merchant includes their secret key:

REQUEST:
POST http://api.payflow.com/v1/payments
Headers:
  X-Api-Key: sk_pay_xYz123AbC456dEf789GhI012JkL345mNo
  Content-Type: application/json

OUR SYSTEM:
1. API Gateway reads header: X-Api-Key = "sk_pay_xYz123..."
2. Compute SHA-256 hash of the key: sha256("sk_pay_xYz123...") = "abc123hash..."
3. Query DB: SELECT * FROM api_keys WHERE secret_key_hash = 'abc123hash...' AND status = 'ACTIVE'
4. Found? → Extract merchant_id → add X-Merchant-Id header → forward to payment-service
5. Not found? → Return 401 Unauthorized

WHY SHA-256 HASH (not store raw key)?
├── If our database is hacked, attacker gets hashes (not actual keys)
├── Hashes cannot be reversed (SHA-256 is one-way)
├── Attacker can't use hashes to make API calls
└── Same principle as password hashing (but SHA-256 not BCrypt because keys are already random)

WHY SHA-256 FOR KEYS (but BCrypt for passwords)?
├── Passwords: Chosen by humans → may be weak → BCrypt adds slowness to resist brute-force
├── API keys: Generated by us → 32+ random chars → already impossible to brute-force
└── SHA-256 is fast (microseconds) → fine for high-volume API key validation
```

## Step 3.1: Understand Key Lifecycle

```
KEY LIFECYCLE:

1. GENERATE:
   POST /v1/merchants/{id}/api-keys?keyType=LIVE
   → Returns: { public_key: "pk_pay_...", secret_key: "sk_pay_..." }
   → secret_key shown ONCE (stored as hash)
   → Status: ACTIVE

2. USE (every API call):
   X-Api-Key: sk_pay_...
   → Validated on every request

3. ROTATE (when merchant wants new keys):
   a. Generate NEW key pair
   b. Update application to use new key
   c. Revoke OLD key
   → Old key immediately stops working

4. REVOKE (compromised or no longer needed):
   POST /v1/merchants/{id}/api-keys/{keyId}/revoke
   → Status: ACTIVE → REVOKED
   → Key immediately stops working (returns 401)
```

## Step 3.2: Add Key Listing and Revocation to MerchantService

**Add these methods to:** `merchant-service/src/main/java/com/payflow/merchant/service/MerchantService.java`

```java
    /**
     * List all active API keys for a merchant.
     * Note: Returns public_key and metadata, NEVER the secret.
     * (We don't even have the secret — only the hash)
     */
    public List<ApiKey> listActiveKeys(String merchantId) {
        // Verify merchant exists
        getMerchant(merchantId);
        return apiKeyRepository.findByMerchantIdAndStatus(merchantId, ApiKey.KeyStatus.ACTIVE);
    }

    /**
     * Revoke an API key (make it permanently unusable).
     * Used when: key is compromised, merchant rotates keys, or merchant leaves.
     */
    @Transactional
    public void revokeApiKey(String merchantId, String keyId) {
        ApiKey apiKey = apiKeyRepository.findById(keyId)
                .orElseThrow(() -> new ResourceNotFoundException("ApiKey", "id", keyId));

        // Security check: key must belong to this merchant
        if (!apiKey.getMerchantId().equals(merchantId)) {
            throw new PayflowException("KEY_NOT_OWNED",
                    "This API key does not belong to the specified merchant",
                    HttpStatus.FORBIDDEN);
        }

        // Already revoked? Ignore (idempotent)
        if (apiKey.getStatus() == ApiKey.KeyStatus.REVOKED) {
            return;
        }

        apiKey.setStatus(ApiKey.KeyStatus.REVOKED);
        apiKeyRepository.save(apiKey);
        log.info("API key revoked: {} for merchant {}", keyId, merchantId);
    }
```

**Add these imports at top of MerchantService.java:**
```java
import com.payflow.common.exception.PayflowException;
import org.springframework.http.HttpStatus;
import java.util.List;
```

## Step 3.3: Add Endpoints to MerchantController

**Add to:** `merchant-service/src/main/java/com/payflow/merchant/controller/MerchantController.java`

```java
    @GetMapping("/{merchantId}/api-keys")
    @Operation(summary = "List all active API keys for a merchant",
            description = "Returns public keys and metadata. Secret keys are never returned.")
    public ResponseEntity<ApiResponse<List<ApiKey>>> listApiKeys(
            @PathVariable String merchantId) {
        List<ApiKey> keys = merchantService.listActiveKeys(merchantId);
        return ResponseEntity.ok(ApiResponse.success(keys));
    }

    @PostMapping("/{merchantId}/api-keys/{keyId}/revoke")
    @Operation(summary = "Revoke an API key",
            description = "Permanently disables the key. It can never be reactivated. "
                + "Generate a new key instead.")
    public ResponseEntity<ApiResponse<Void>> revokeApiKey(
            @PathVariable String merchantId,
            @PathVariable String keyId) {
        merchantService.revokeApiKey(merchantId, keyId);
        return ResponseEntity.ok(ApiResponse.success());
    }
```

**Add import at top:**
```java
import java.util.List;
```

## Step 3.4: Verify with curl

### List keys:
```cmd
curl http://localhost:8082/v1/merchants/merch_aB3dE5fG7h/api-keys
```

**Expected (200):**
```json
{
  "success": true,
  "data": [
    {
      "id": "key_Mn2kP9wQr5",
      "merchantId": "merch_aB3dE5fG7h",
      "keyType": "LIVE",
      "publicKey": "pk_pay_51a2b3c4d5e6f7g8h9",
      "keyPrefix": "sk_pay_xYz1",
      "status": "ACTIVE",
      "createdAt": "2026-07-20T10:30:00Z"
    }
  ]
}
```

Note: `secretKeyHash` is in the entity but Spring/Jackson serializes it. In production you'd use a DTO to exclude it. For now it's fine — the hash is useless without the original key.

### Revoke a key:
```cmd
curl -X POST http://localhost:8082/v1/merchants/merch_aB3dE5fG7h/api-keys/key_Mn2kP9wQr5/revoke
```

**Expected (200):**
```json
{
  "success": true,
  "timestamp": "2026-07-20T10:35:00Z"
}
```

### Verify key is revoked:
```cmd
curl http://localhost:8082/v1/merchants/merch_aB3dE5fG7h/api-keys
```
**Expected:** Empty list (revoked keys not returned).
